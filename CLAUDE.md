# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What This Is

A World of Warcraft TBC Classic Anniversary addon for a Hunter character. The addon folder (`ExsarAddon/`) is the entire repository — WoW loads it from `Interface/AddOns/ExsarAddon/`.

## Installing / Testing

Copy (or symlink) the repo folder into your WoW client's addon directory:
```
World of Warcraft/_classic_/Interface/AddOns/ExsarAddon/
```
Then reload the UI in-game with `/reload`. There is no build step.

## Quality Checks

Run these before committing changes:
- `busted` — runs unit tests (380 tests covering ExsarLogic and MakeDB)
- `luacheck .` — static analysis; should report 0 warnings / 0 errors
- `luac -p *.lua` — syntax check (redundant with luacheck but faster)

The `.luacheckrc` config declares all WoW API globals, addon cross-file globals, and test file exceptions. When adding new WoW API calls, add them to the `read_globals` list in `.luacheckrc`.

## In-Game Commands

- `/exsar config` — open the configuration panel (also available via Interface → AddOns)
- `/exsar unlock` / `/exsar lock` (aliases `unlockall` / `lockall`) — unlock or lock **every** widget at once, via `ExsarAddon.SetAllLocked`. Also exposed as the "Unlock all" / "Lock all" buttons pinned above the config sidebar. Refused in combat
- `/exsar reset` — reset the cooldown tracker widget position
- `/exsar errdump` — open the captured Lua-error log (newest first) in a copy-paste window; `/exsar errclear` wipes it; `/exsar errcapture` toggles capture. See `ErrorCapture.lua`

**Keeping CLAUDE.md in sync:** Any change that adds a new widget, removes a widget, renames a module, alters its responsibilities, or changes its persisted settings MUST be accompanied by an update to this file. Before finishing any such change, cross-reference the file table, the SavedVariables list, and any module-specific structure notes against the code, and update whatever is now stale. Treat CLAUDE.md as a first-class deliverable of the change — a code change that leaves CLAUDE.md out of date is incomplete.

**Keeping README.md in sync:** Any change that affects user-facing behavior — adding/removing/renaming a widget, changing tracked items or buffs, altering visual effects, modifying thresholds or defaults, changing detection algorithms, or updating slash commands — MUST be accompanied by a corresponding update to `README.md`. Cross-check the widget's one-liner description and bullet-point notes against the code and update whatever is now stale. Treat `README.md` as a first-class deliverable alongside `CLAUDE.md`.

**Adding a new feature module:**
1. Create a new `.lua` file and add it to `ExsarAddon.toc` (after `ExsarUI.lua` and `Core.lua`)
2. Call `ExsarAddon.RegisterModule({ name = "...", BuildConfig = function(parent, y) ... return y end })`
3. Call `ExsarAddon.AddSlashCommand(cmd, fn)` for any slash sub-commands
4. Store settings under `ExsarAddonDB.<moduleName>` via `ExsarUI.MakeDB("moduleName")`
5. Add a row to the file table above and a `ExsarAddonDB.<moduleName>` entry to the SavedVariables list below

**Code reuse principle:** Always prefer using shared helpers from `ExsarLogic.lua` and `ExsarUI.lua` over writing bespoke code. When building a new widget, check the shared libraries first — most common patterns are already available. If you write new logic that could be reused by other modules, extract it into the appropriate shared library: pure logic goes in `ExsarLogic.lua` (testable without WoW API), UI construction goes in `ExsarUI.lua`. Never duplicate code across module files. Refer to UI effects by their standard names (see below) and always use the shared implementation.

**Testability principle:** Design new code to be unit-testable wherever possible. Extract logic into pure functions in `ExsarLogic.lua` so it can be tested with `busted` without WoW API mocks. When writing ExsarUI helpers, accept dependencies as parameters (tables with callable fields) rather than hardcoding WoW API calls, so they can be tested with lightweight stubs. Every new function added to `ExsarLogic.lua` should have corresponding tests in `tests/test_logic.lua`. New ExsarUI helpers should have contract tests in `tests/test_makedb.lua` (or a new test file) using stub tables. Run `busted` and `luacheck .` before considering any change complete.

| **Slash Flourish** | An arcing crescent blade-swipe with pseudo-3D depth, rendered as a **brush stroke** — a dense line of overlapping soft round dots (a soft-circle texture, additive-blended: a wide glow halo + a bright core, ~89 stamps per layer) stamped along the pure `ExsarLogic.SlashArcPoint` Bézier, so there are **no straight facets or hard corners**, just soft glowing edges and a rounded tip. Sweeps diagonally (base lower-**left** → tip upper-**right**) with the belly bulging **right**, in a **teardrop/comet** silhouette — a fat rounded belly low near the base tapering to a fine point at the leading tip (`ExsarLogic.SlashArcThickness`, so fat-bottom → thin-top reads as a blade going away-and-toward). `ExsarLogic.SlashArcPoint` is the un-rotated base curve (bows right, base lower-right → tip upper-left); `CreateSlashEffect` applies a clockwise `rotation` opt (default 45°) on top to get the on-screen diagonal. Reads as arcing **forward toward the enemy**, not flat: `ExsarLogic.SlashArcDepth` bows the leading half toward the viewer (forward stamps drawn bigger + lifted) and the whole swipe grows via a toward-you zoom as it draws (`depth` opt scales the effect, 0 = flat). Draws itself bottom→tip, drifts up, and fades over `duration` (0.4s default; the weave helper passes 0.8s for a quick, punchy sweep). Lives on its own UIParent-child frame anchored to the widget (fires even when hidden). Reveal/fade curve is the pure `ExsarLogic.SlashAnim`. Used by MeleeWeaveHelper's Windfury proc flourish. The **soft-dot texture** (`opts.dotTexture`, generic default `Interface\GLUES\MODELS\UI_Tauren\gradientCircle` — a soft radial whose ADD-blended edges add nothing, so it falls off softly by construction, unlike a hard alpha-mask disc which just stacks into a fatter hard blob) is the real diffuseness lever and is swappable live via `slash:SetTexture(path)` / `/exsar slashtex` (the browser Slash-Lab preview canNOT reproduce texture hardness — verify diffuseness in-game). **MeleeWeaveHelper passes `dotTexture = Interface\Cooldown\star4`** (chosen in-game). | `ExsarUI.CreateSlashEffect(anchor, opts)` → `slash:Trigger()` / `slash:SetTexture(path)` |

When adding a new widget that needs a highlight, border, alert, or status indicator, use one of these standard effects rather than creating a bespoke visual.

**Sound effects pattern:**
Several modules play `PlaySound(soundKitID, "Master")` on state transitions (e.g. aggro gained, low HP threshold crossed, melee range entered/left). Use `PlaySoundFile(fileDataID, "Master")` instead when the sound is identified by a FileDataID rather than a SoundKit ID (see the API note below). Standard pattern:
- Track the previous state to detect edges (e.g. `wasActive` → `isActive`)
- Use a cooldown timer (`GetTime() - lastSoundTime >= COOLDOWN`) to prevent spam
- Gate behind a per-module DB flag (e.g. `db.lowHpSound ~= false`) with a config checkbox
- Defaults to enabled (`~= false` check, so `nil` counts as enabled)

**Ranked item fallback** (`ConsumableBuffWidget`):
Items with a `ranks` field (array of `{ name, id, buffId }` ordered highest-first) automatically show the highest rank with bag stock, falling back to the highest rank (greyed out) when none are available. Uses `ExsarLogic.SelectBestRank(ranks, getCount)` for the selection logic. Buff detection checks all rank buff IDs. Secure button `item` attribute is updated out of combat when the active rank changes.

**Weapon enchant tracking** (`ConsumableBuffWidget`):
Items with `weaponEnchant = true` (Adamantite Sharpening Stone, Adamantite Weightstone) are tracked via `GetWeaponEnchantInfo()` instead of the buff list. Both weapon hands are read; `ExsarLogic.MinWeaponEnchantRemaining(enchantId, ...)` returns the soonest-to-expire hand carrying the matching `enchantId`, so a stone applied to a dual-wield pair shows the timer that will run out first. `buffDuration` is hardcoded (3600s) for the sweep animation since the API reports only remaining time, not total duration. When the soonest-expiring hand switches, the >2s sweep-start guard catches the jump.

**`RangedSwingTimer.lua` structure:**
- Bar drains from full width to zero width (centered) over the ranged weapon speed cycle; resets on each Auto Shot

A single-ID check silently misses every rank

The bar redraws after the FD-end restart even though `shooting` is false (OnUpdate draws whenever the weapon cooldown is running)
- Bar color: blue (safe) → red (stop moving / aim window active)
- `SPELLS_CHANGED` triggers a 0.5s deferred `RefreshAll()` to handle talent-driven speed changes
- Delay indicator (`ExsarLogic.AutoShotDelay`, pure/tested): recomputed every OnUpdate frame, two regimes — a cast ending past the due time shows the predicted clip in red (`(0.34)`, static while the cast runs), and a shot past due that hasn't fired (melee weave with auto-repeat off, moving, dead zone) shows a live-growing orange counter (`(+1.3)`). Gated on `S.autoFired` (cleared on PLAYER_REGEN_ENABLED + Feign Death — NOT on combat enter: the pull's first auto shot is what causes combat, so it fires just before PLAYER_REGEN_DISABLED, and clearing there wipes the first shot's flag) — NOT on `S.shooting`, because melee weaving toggles auto-repeat off (verified in-game), which is exactly the case the counter must cover. Overdue readings under `CLIP_OVERDUE_GRACE` (0.2s) are suppressed: `UNIT_SPELLCAST_SUCCEEDED` lags the server, so every normal cycle reads ~0.1s late just before the event lands. The widget stays visible while overdue (the cycle-complete hide is skipped when a delay is showing). Future refinement: `UNIT_SPELLCAST_FAILED_QUIET` fires for Auto Shot (75) when an attempt fails with auto-repeat ON (each failure costs ~0.5s before the client retries — see WeaponSwingTimer-SixxFix's `OnUnitSpellCastFailedQuiet`); not currently used

**`CastBar.lua` structure:**
- `autoAimTicker` — always-running frame that detects the Auto Shot aim window from `lastAutoTime + autoSpeed - AUTO_AIM_TIME` and shows a green bar
- Swing-cycle resets re-anchor `lastAutoTime` (mirrors the RangedSwingTimer model — keep the two in sync): an Aimed Shot landing anchors a full cycle from the landing; Feign Death sets `fdReset` + clears the anchor, and the **FD buff fading** (`UNIT_AURA` + `ExsarUI.PlayerHasBuff`) anchors a full cycle from FD end (`START_AUTOREPEAT_SPELL` keeps a fallback anchor, but it does not reliably re-fire after FD). While `fdReset` is pending the ticker's Case B (lastAutoTime == 0 → "first shot fires on stop") is suppressed — after FD that state means "cycle restarts when feign ends", not "instant shot"
- Regular casts (Aimed Shot, Steady Shot) detected via `UNIT_SPELLCAST_START` → `UnitCastingInfo`
- Multi-Shot detected via `COMBAT_LOG_EVENT_UNFILTERED` / `SPELL_CAST_START` using `CombatLogGetCurrentEventInfo()` (required for TBC Classic Anniversary modern client; old variadic-args approach does not work)
- `UNIT_SPELLCAST_FAILED` / `UNIT_SPELLCAST_INTERRUPTED` → brief red flash before hiding
- Bar colors: green (Auto Shot aim), gold (Aimed Shot), blue (Steady Shot), orange (Multi-Shot)
- **Auto-shot HOLD warning (retry-timer cue).** When the Auto Shot aim bar reaches its predicted end (`now >= C.endTime`) but the shot hasn't fired yet — the hidden **retry timer** window (see "The Retry Timer" in the Hunter timing reference) — the bar does NOT hide. Instead `BeginHold(now)` enters a HOLD state: the bar stays full + amber and a pulsing **orange glow** (`holdGlow`, `ExsarUI.CreateGlow` on BACKGROUND) surrounds the whole widget, telling the player *"wait, don't act — the auto is still pending"* (acting here clips the shot). The glow pulses via `ExsarLogic.PulseAlpha`; `ExsarLogic.ShouldShowHoldWarning(autoActive, moving, now, holdEnd)` (pure/tested) gates it. HOLD ends when the shot fires (`EndHold()` in the `UNIT_SPELLCAST_SUCCEEDED` auto branch — its whole purpose is to bridge the gap until this event), on movement (cancels the pending shot), on `STOP_AUTOREPEAT_SPELL`/Feign Death, when a new cast supersedes it (`ShowBar`), or at the `HOLD_MAX` (0.85s) safety cap so a missed fire event can't strand the glow. **Self-isolating property:** because `C.endTime` (from `lastAutoTime + autoSpeed`) and the fire event are both shifted by the same event latency, a clean cycle shows a near-zero glow while the glow *duration tracks the real retry delay*. Only entered while stationary + auto-repeat on. Toggle: `ExsarAddonDB.castBar.holdWarning` (default ON; "Auto-shot HOLD warning" config checkbox), cached as `C.holdWarn`.

**`RangeToTargetWidget.lua` structure (and the range-bracketing approach for future range widgets):**
- **Core fact:** WoW exposes no exact distance to a unit (anti-radar-hack). Distance can only be *bracketed* by probing a set of harm range checks with known thresholds — the technique LibRangeCheck / RangeDisplay use. See the `IsItemInRange` / `IsSpellInRange` entries under "Key WoW API Used" for the per-call rules (combat permissions, return shapes, the min-range pitfall).
- `CHECKERS` — an ascending ladder of `{ range, spell= | item= }`. `spell` entries (Wing Clip, 5yd) use `IsSpellInRange`; `item` entries use `IsItemInRange` with item IDs the player need not own. **Only no-minimum harm checks are valid** for the *middle* of the ladder: a spell/item with a minimum range (Auto Shot's dead zone) returns out-of-range when *too close* as well as too far, which corrupts the lower bound — that's why Wing Clip (pure melee) is the only mid-ladder spell checker. Item IDs come from the LibRangeCheck harm-item tables; IDs not present in the TBC client return nil and are skipped.
- **Top-end Auto Shot checker + Hawk Eye (`rangedMax`).** The single `autoShotChecker` at the top of the ladder is `{ range = <maxRange>, spell = "Auto Shot" }`. Its `IsSpellInRange("Auto Shot")` inherently respects the player's real shooting range — 35yd base **+2yd per Survival Hawk Eye rank** — which no fixed-range item can express. `RefreshShootingRange()` scans the player's own talents (`GetTalentInfo`) for "Hawk Eye", computes `rangedMax = ExsarLogic.MaxShootingRange(rank)` (35 + 2/rank, pure/tested), and writes it into both `autoShotChecker.range` (so the bracket label/upper bound extend, e.g. `"35-41 yd"`) and the `rangedMax` passed to `RangeZone` (so the IN RANGE→FAR boundary moves out). Runs on `PLAYER_ENTERING_WORLD` / `PLAYER_TALENT_UPDATE` / `CHARACTER_POINTS_CHANGED` / `SPELLS_CHANGED`. Auto Shot's own 5yd dead-zone corruption (reporting out-of-range when *too close*) is self-healing: Wing Clip (5yd) reports in-range simultaneously, and `ComputeRangeBracket`'s non-monotonic guard drops the contradictory far lower bound → "melee".
- Polled at 0.1s (range has no event) + `PLAYER_TARGET_CHANGED`. Each poll normalizes every check to `true`/`false`/`nil` (1/0/nil for spells, bool/nil for items) and feeds the parallel `results` table to `ExsarLogic.ComputeRangeBracket(checkers, results)`.
- `ExsarLogic.ComputeRangeBracket` → `minR, maxR`: `maxR` = smallest in-range threshold (upper bound), `minR` = largest out-of-range threshold (lower bound). nil results are skipped, so invalid/restricted checks merely widen the bracket (graceful degradation — worst case collapses to Wing Clip's binary ≤5 / >5). A contradictory lower bound (non-monotonic jitter where a near check is in-range but a farther one is out) is dropped in favor of the more-trustworthy upper bound.
- `ExsarLogic.FormatRangeBracket(min, max)` → display string: `"5-8 yd"`, `"0-5 yd"` (within nearest checker / in melee), `"35+ yd"` (beyond furthest checker), `"?"` (nothing usable). `ExsarLogic.MaxShootingRange(hawkEyeRank, base=35)` → max shooting range (pure/tested). `ExsarLogic.RangeZone(min, max, meleeMax=5, weaveMax=8, rangedMax=35)` → `"melee"`/`"weave"`/`"inrange"`/`"far"`/`"?"`, driving the colored zone label (orange/green/blue/red).
- Visibility: shown whenever the player has an attackable target (alive + `UnitCanAttack`), **not** combat-gated (unlike MeleeRangeIndicator), so it can be used to set up pull distance; also shown while unlocked.
- **Reuse for future range widgets:** the pure logic (`ComputeRangeBracket`, `FormatRangeBracket`, `RangeZone` in `ExsarLogic.lua`) is fully unit-tested — build new range widgets on it directly. The probe-and-normalize loop and the `CHECKERS` ladder are currently widget-local; when a second range-based widget is added, extract that step into a shared helper (e.g. `ExsarUI.GetRangeBracket(unit, checkers)`) rather than duplicating the loop, per the code-reuse principle.

**`RaidTargetWidget.lua` structure:**
- **Why assist-only — the hard platform constraint (do NOT try to re-add icon/mark targeting).** You cannot make a secure button target an *arbitrary marked mob* in combat. Targeting is a protected action: in combat the unit must come from a value baked into the button **before** combat — either a literal constant or a token the game's own secure engine re-resolves (`"raid3target"`). An addon-computed "whoever is on the square right now" choice is exactly what combat forbids, and WoW exposes **no macro conditional for "the unit wearing raid mark N"**. The previous icon-row mechanism (bind `raidNtarget` of *some raider* currently on the marked mob) failed because `raidNtarget` tracks the *raider*, not the mob — the instant that raider retargets (constant in AoE trash) the binding follows them, and it can't be rewritten in combat. Diagnostic logs showed every miss had the bound token pointing at a different unit than the mark. The **only** combat-stable handle is a *stable referent*: a person who reliably stays on their mob (a tank). So the widget assists **people**, not marks.
- **Targeting model — static secure binding + live token.** Every row is a `SecureUnitButtonTemplate` with a fixed `type1="target"` and a `unit` attribute (e.g. `"raid3target"`) written **ahead of time, out of combat** (via `ExsarUI.SecureSetAttribute`, deferred under lockdown). The secure engine resolves that token **live on every click**, so the row tracks the member's current target with no combat-time rewrite. **Never set a secure button's `type`/`unit`/`macrotext` from `PreClick` or in combat.**
- **Tracked-member rows** (vertical list, one member per row, pool size `MAX_ROWS` = 12). `GatherRoster()` builds the group (raid via `GetRaidRosterInfo`, party via `party1..4`), flagging tanks via `UnitGroupRolesAssigned(unit) == "TANK"` → Main-Tank assignment (`GetRaidRosterInfo` role `"MAINTANK"` / `GetPartyAssignment("MAINTANK", unit)`). `ExsarLogic.ComputeAssistList(roster, ManualNameSet())` (pure, unit-tested) returns the **union** of role-flagged tanks and members named in the manual set (`ExsarLogic.ParseNameSet` over `rDB().manualTanks`), in roster order, deduped. Each row binds `unit="raidNtarget"` (the member's current roster index) → clicking assists them. The row shows: the member's portrait + class-colored name (top line, dimmed when offline), the raid mark on the member's **current target** + that target's name (hostility-colored) + the target's health bar/%; the gold pulsing border glows when the member's target == the player's current target. "(no target)" + hidden bar when the member has nothing targeted. Player is excluded (self-assist no-ops).
- **Roster reshuffle handling.** A member's `raidN` index changes if the raid leader moves them between subgroups. `GatherRoster` re-resolves every member from the live roster each scan (0.3s poll + `GROUP_ROSTER_UPDATE`), and a row rebinds (`SecureSetAttribute`) whenever its member's `unit` token changes — out of combat, where the write is allowed. So assist targets follow the right *person* across reshuffles.
- **Combat-safety of layout.** Repositioning/showing/hiding secure buttons is protected, so `Layout()` (positions, `frame:SetSize`/`ReAnchor`, `Show`/`Hide`) runs **only out of combat**; in combat the widget still updates visuals (portrait/health/mark/name/glow) and defers binding writes, but does not reflow. A member who first appears mid-combat doesn't get a row until combat ends.
- Slash: `/exsar rtreset` resets position. (The old click-miss diagnostics — `rtdebug`/`rtdump`/`rtclear`, `clickMissLog` — were removed with the icon mechanism they debugged; the assist path is the proven-reliable one.)

**`PetHappinessTracker.lua` structure:**
- Tier reconciliation delegates to `ExsarLogic.ReconcileHappinessTier`, which preserves the estimate when it is already inside the API-reported tier's range and only snaps to the crossed boundary when outside. This prevents feed-induced tier-ups from clobbering the exact `+amount` arithmetic (previous bug: pet at 695, feed +8 → estimate 703 → API reports tier 3 → code overwrote estimate to `TIER_MIN[3]=700`, producing a stuck `0.0s` display).
- Passive decay delegates to `ExsarLogic.ApplyHappinessDecay`, which clamps the estimate at `TIER_MIN[S.tier]`. Since the WoW API is authoritative on tier, the real value cannot be below that floor while the API still reports the current tier. Without the clamp, estimate drifted past the floor and the display collapsed to `0.0s` until `UNIT_HAPPINESS` re-anchored it.
- `S.guessing` is set when `SeedEstimate` cold-seeds with no saved data (the tier midpoint is used only as an internal decay fallback). The display renders a faint `?` instead of a fake timer until a trusted anchor is observed. `guessing` clears when `ReconcileHappinessTier` sets `anchored = true` (observed tier crossing) or a feed-at-max is detected. Persisted as `savedGuessing` so the state survives `/reload`.
- Debug ring buffer (`hDB().debugLog`, cap = 30) captures state transitions so the user can run `/exsar phdump` after observing a surprising display. Event types: `seed` (cold-start / restored-from-saved / saved-tier-mismatch), `tier` (tier flip or same-tier snap from `CorrectToTier`), `feed` (every Feed Pet bite detected via `SPELL_PERIODIC_ENERGIZE`), `clamp` (decay-floor pin — logged only on the transition into clamped state to avoid flooding while pinned), `penalty` (dismiss / death). Default ON; toggle with `/exsar phdebug`. `/exsar phdump` renders the buffer into a modal copy-paste window via `ExsarUI.ShowCopyableText`. `/exsar phclear` wipes the buffer. `FormatPHEntry(entry)` is shared between the live chat printer (`LogPH`) and the dump renderer.
- `S.wasDecayClamped` tracks whether the previous decay tick hit the floor, so `LogPH` for `clamp` events fires once per clamp run, not every second while pinned.

**`RaidDebuffTracker.lua` structure:**
- `TRACKED_DEBUFFS` — array of `{ key, name, iconSpell, auras = { name, ... } }`, a mix of **grouped categories** and **specific debuffs**. `key` is the stable id for the per-debuff enable map (reordering the table never scrambles saved toggles); `iconSpell` is used only to fetch the icon texture via `GetSpellInfo` (resolved on load / `SPELLS_CHANGED`); `auras` is the list of aura names that satisfy the entry — present if **any** alias is on the target. A grouped entry (e.g. "Armor Debuff") lists every aura that covers the category and is only flagged missing when *none* are up; a specific entry (e.g. "Hunter's Mark") just lists its own name (also catching all ranks).
- Scans the target with `UnitDebuff("target", i)` **without** the `"PLAYER"` filter (raid debuffs are cast by other players) and matches by **name** to catch all ranks/sources.
- `ExsarLogic.ComputeDebuffStatus(tracked, isEnabled, present, requiredCasterFor)` (pure, unit-tested) → one entry `{ def, key, satisfied, aura }` per ENABLED tracked debuff in input order (`aura` = the satisfying alias aura name, used to look up its live duration/expiration for the bar). `ExsarLogic.ComputeMissingDebuffs` is now a thin filter over it (the unsatisfied entries) and stays unit-tested. `present` maps aura name → `true` (present, caster unknown) or a caster GUID string. `ExsarLogic.DebuffBarColor(remaining, duration)` (pure, unit-tested) → r,g,b for a draining present-debuff bar: blue >50%, yellow >20%, orange ≤20% of duration remaining; nil/0 duration → blue (treated as full). `ExsarLogic.RaidDebuffsShouldShow({ enabled, inCombat, inRaid, hasTarget, showOutOfCombat, showOutOfRaid, unlocked })` (pure, unit-tested) gates whether the widget is **active**: always active when unlocked (config preview); otherwise requires enabled + a target ALWAYS, plus in-combat (unless `showOutOfCombat`) and in-raid (unless `showOutOfRaid`). When inactive the frame is hidden; when active `ApplyLayout` runs and the frame is always shown — so the persistent "Raid debuffs:" title is the user's cue that the widget is live, even when the row list is empty. **While unlocked the target scan is skipped (`present`/`timing` left empty), so every enabled debuff lists as missing — a deterministic positioning/testing preview independent of the current target.**
- **Per-row timer bars.** The 0.2s scan builds, alongside `present`, a parallel `timing` map (aura name → `{ duration, expTime }`) from returns 5/6 of `UnitDebuff` (works for others' debuffs on the modern Anniversary client). Each present row drives a StatusBar: `SetMinMaxValues(0, duration)` + `SetValue(remaining)` drains it, `DebuffBarColor` recolors it, and `FormatCooldown(remaining)` fills the timer text (cached per slot to avoid `SetText` churn). Rows stay in tracked order (stable, never re-sorted by remaining). The name + timer are FontStrings overlaid on the bar; uniform bar width = widest enabled name + `TIMER_RESERVE`.
- **Caster matching (talent-gated debuffs):** some debuffs only deliver their hunter-relevant bonus when the caster is **talented**, and that talent is unreadable from the aura (the aura name/spellId is identical talented or not). Two such debuffs: **Improved Faerie Fire** (druid talent → +hit) and **Judgement of the Crusader** (paladin talent *Improved Seal of the Crusader* → +crit to all attacks against the judged target). The fix: identify the specced player(s) and match the debuff's **caster**. Driven by the **`CASTER_MATCHED`** table, keyed by debuff `key`: `{ talent, class, guidKey, nameKey, label }`. Adding another talent-gated debuff is one row.
  - **Matching:** the scan resolves each debuff's caster token (7th return of `UnitDebuff`) to a GUID via `UnitGUID`; `RequiredCasterFor(key)` returns the **union** (manual pin ∪ auto-detected) of accepted caster GUIDs as a set, fed into `ComputeMissingDebuffs`. The aura satisfies the entry only if cast by an accepted GUID **or** the caster is unknown (lenient — avoids false alarms when the token is `nil`/out of range); cast by a *known different* player (e.g. a feral applying FF for armor) it's still flagged missing. When nobody is designated, any caster counts.
  - **Auto-detect (talent inspect):** gated by the `autoDetect` setting (`IsAutoDetectEnabled()`, default ON) — when off, both `RefreshInspectQueue` and `ProcessInspectQueue` early-out so no inspect ever fires. `RefreshInspectQueue` (on `PLAYER_ENTERING_WORLD`/`GROUP_ROSTER_UPDATE`) collects raid members of the `INSPECT_CLASSES` (union of `CASTER_MATCHED` classes) into `inspectWanted`; a 2s poller (`ProcessInspectQueue`) calls `NotifyInspect` on a reachable member and `INSPECT_READY` → `OnInspectReady` reads inspect talents (`GetTalentInfo(t, i, true)`) into a `{name, rank}` list, then for every `CASTER_MATCHED` key whose `class` matches the inspected unit uses `ExsarLogic.FindTalentRank` (pure, unit-tested) to check that key's talent rank > 0, caching the GUID in the in-memory `autoGuids[key]` / `autoNames` (not persisted — re-detected each session to handle respecs). Only needs to catch a player in inspect range **once**; the cached GUID then matches their debuff anywhere. **Verified working on Anniversary 2.5.5** (auto-detected a boomkin's Improved Faerie Fire).
    - **Spam-avoidance gating (critical):** `NotifyInspect` errors loudly ("unknown unit" / "out of range") when the unit is beyond inspect range, and that error path never fires `INSPECT_READY`, so a naive retry loop hammers the same far-away raider once per stale-timeout. `CanInspect` does **not** check range. `ProcessInspectQueue` therefore gates on **`CheckInteractDistance(unit, 1)`** (real ~28yd inspect range), skips while Blizzard's `InspectFrame` is shown (single inspect channel), enforces one inspect in flight + 3s stale-pending timeout, and applies a per-GUID **backoff** (`inspectBackoff[guid]`, `INSPECT_BACKOFF = 10s`) so an occasional error can't stream. Net effect: only ever inspect someone actually in range; far raiders are simply retried later when they move close (raid stacking/movement brings everyone within 28yd eventually). **Do not gate inspect on `CanInspect` alone — that was the original spam bug.**
  - **Manual pin (capture-from-target):** per-debuff config button stores `<guidKey>`/`<nameKey>` (persisted), as a guaranteed fallback/override; warns if the targeted player's class doesn't match.
- **Combat-log `SPELL_AURA_APPLIED` source tracking cannot replace inspect** — it identifies the caster but not whether they are *talented* (the whole point). Inspect is the only path to the talent.
- Vertical list: a fixed title FontString at top, then one row per ENABLED tracked debuff (present or missing). Each row is a `[icon-holder] [StatusBar]` frame; the icon comes from `iconSpell` (resolved via `GetSpellInfo`, retried on `SPELLS_CHANGED`), and the bar carries the name (left-overlaid, colored from `presentColor`/`PRESENT_COLOR` when present or `color`/`MISSING_COLOR` when missing) and the timer (right-overlaid). Missing rows fill the bar solid dim-red (`MISSING_BAR_COLOR`) with no timer. `ApplyLayout` sizes the frame to the widest of the title / rows and stacks rows top-down.
- Combat state tracked via `PLAYER_REGEN_DISABLED`/`PLAYER_REGEN_ENABLED` (seeded from `InCombatLockdown()` on `PLAYER_ENTERING_WORLD`); raid state via `IsInRaid()` refreshed on `GROUP_ROSTER_UPDATE`. Polled at 0.2s plus `UNIT_AURA` (target), `PLAYER_TARGET_CHANGED`.
- Config: enable-widget checkbox, **"Show out of combat" / "Show out of raid" checkboxes** (both default OFF; persist to `ExsarAddonDB.raidDebuffs.showOutOfCombat` / `showOutOfRaid`, stored `true` only when enabled — `IsShowOutOfCombat()`/`IsShowOutOfRaid()` = `== true`), scale, lock, one checkbox per tracked debuff (default ON, disable per raid composition), an **"Auto-detect talented casters (inspect)" checkbox** (default ON; persists to `ExsarAddonDB.raidDebuffs.autoDetect`, `IsAutoDetectEnabled()` = `~= false`), reset button. Per-debuff state persists to `ExsarAddonDB.raidDebuffs.debuffs[<key>]`. When auto-detect is off, `ProcessInspectQueue`/`RefreshInspectQueue` early-out (no inspects fire at all) — already-cached `autoGuids` are kept (still valid), only new detection stops; manual pin still works.
- **`TRACKED_DEBUFFS` (the tracked set):** "Armor Reduction" (grouped — Sunder Armor OR Expose Armor), "Curse of Recklessness" (specific; warlock armor curse that stacks on top), "Improved Faerie Fire" (Faerie Fire aura + caster matching, see above), "Judgement of Wisdom" (specific; paladin, British spelling in-game), "Judgement of the Crusader" (caster-matched — paladin *Improved Seal of the Crusader*, British spelling), "Hunter's Mark" (specific). To add another: append an entry (grouped via multiple `auras`, or caster-matched by also adding a `CASTER_MATCHED` row).

**`ExsarUI.CreateActionBar` (action bar engine) structure:**
The shared engine behind `UsableItemsWidget`, `PetManagementWidget`, and any future themed bars (Traps/Shots/Utility). Each widget file is now just an **action table + a `CreateActionBar{...}` call**; the engine owns the chassis. **Add a new bar by writing an action table + a few `Bindings.xml` lines + one `CreateActionBar` call — do NOT hand-write another bar widget.** The field reference lives in the engine's header comment in `ExsarUI.lua`.
- **Slot kinds.** A slot is `"item"` kind (UsableItems behavior — tracks bag stock via `GetItemCount`, dims when out of stock or on cooldown, optional rank/alternate swapping, gold border ring) or `"macro"`/`"spell"` kind (PetManagement behavior — always present, greyed by a pet-state/`requires` predicate, sweep from item/debuff/GCD). Kind is `action.type` or inferred (`macro` field → macro, `spell` → spell, else item).
- **Mechanism vs policy.** The engine owns *mechanism* — secure `SecureActionButtonTemplate` slots (`RegisterForClicks("AnyUp","AnyDown")`), layout, sweep/count/hotkey-label rendering, **Dimmed** grey-out, the keybind bridge, slash reset, scale/lock/reset config rows, `RegisterModule`, event+poller wiring. *Policy* is the per-slot action spec: declarative fields cover the common cases (`icon`/`iconItem`/`iconSpell`/`dynamicIcon`, `spells` [talent-gated, see below], `trinketSlot` [equipped 13/14], `ranks`, `alternates`, `countItem`/`countCharges`, `cooldownItem`/`cooldownSpell`/`cooldownTrinket`/`cooldownDebuff`/`gcd`, `requires`, `activeBuff`, `borderColor`, `hideWhenEmpty`/`groupFallback`), the bar-level `dimOnCooldown` (dim macro/spell slots while a real CD runs), `rangeCheck` (out-of-range red shade — see below) and `manaCheck` (out-of-mana blue shade — see below), and **escape-hook callbacks** carry the genuinely bespoke 20% (`resolveActive`, `getCooldown`, `getCount`, `resolveIcon`, `isEnabled`, `isActive`, `resolveBorderColor`, `resolveMacro`, `tooltip`, `postClick`). **`postClick(s)`** fires on the slot's *press* (installed as a `PostClick` script — never `OnClick`, which taints a secure button; slots register both edges, so the release is filtered out by `down == false`. **Verified in-game on Anniversary 2.5.6:** `down` arrives as a real boolean for keybind-driven clicks, so the filter fires the hook exactly once per press — had it been `nil`, the stamp would land on key-*up* instead). Used by `CoreCombatWidget`'s Raptor slot to stamp the weave-macro press on the shared melee tracker. `activeBuff` (a player buff name) / `isActive(s)` compute a per-slot `s.active`, which drives the chosen active indicator (`opts.border` gold ring or `opts.activeAnts` marching-ants border — animated on a dedicated always-on ticker). Action/spell slots highlight **only** when they define one of these predicates (e.g. the current aspect via `activeBuff`; the equipped weapon/pole via `isActive` in `UtilitiesWidget`); slots with neither never highlight, so enabling `border`/`activeAnts` on a bar lights up only the slots that opt in. **Per-slot border opt-in.** A single warning slot on an otherwise borderless bar (e.g. Devilsaur Prep on the pet bar) can declare a static `borderColor = {r,g,b,a}` or a dynamic `resolveBorderColor(s, petState) -> {r,g,b,a} | nil`; the engine lazily creates the border ring for that slot only. The dynamic hook fully overrides `isActive`/`activeBuff` — returning a color shows + recolors the border, `nil` hides it, so one slot can flip between multiple warning states (Devilsaur Prep yellow "USE!" vs red "UNEQUIP!"). **Per-slot dynamic macrotext.** A macro-kind slot whose body depends on live state can implement `resolveMacro(s, petState) -> string` instead of `macro`; the engine queues a combat-deferred `SecureSetAttribute` whenever the returned text changes (writes only on change, so the SavedVariables/secure attr queue stays clean). When tempted to add an engine flag, prefer a per-slot closure unless a *second* bar would want it. Pure selection logic stays in `ExsarLogic` (`SelectBestRank`, `SelectFirstInStock`, `CooldownState`, `PetActionEnabled`, `PetStateKey`, `DevilsaurStage`).
- **Dual-edge macro slots (`macroDown` / `macroUp`) — the Grounded technique.** A slot can run one macro body on key **down** and a different one on key **up** by declaring `macroDown` + `macroUp` in place of `macro`. The engine stores both as `macrotextDown`/`macrotextUp` attributes and installs a **`SecureHandlerWrapScript`** on `OnClick` that copies the right body into `macrotext` before `SecureActionButton_OnClick` reads it. **The swap must happen inside that restricted-environment snippet:** a snippet may `SetAttribute` *in combat*, whereas ordinary Lua cannot — `ExsarUI.SecureSetAttribute` would defer the write to `PLAYER_REGEN_ENABLED`, useless for a per-press swap. `SecureHandlerWrapScript` **stacks**, so install it exactly once per slot (`AB_SetupDualEdge` at construction); the `PLAYER_REGEN_ENABLED` re-apply path calls `AB_ApplyDualEdge`, which rewrites only the two bodies. A dual-edge slot's `macrotext` is owned by the snippet — never write it from Lua. The only user is `CoreCombatWidget`'s Raptor Strike weave slot, whose macros flip the **global** `ActionButtonUseKeyDown` CVar (press → 0, release → 1) so that both edges dispatch a secure action; `CoreCombatWidget` repairs the CVar to 1 on `PLAYER_ENTERING_WORLD`/`PLAYER_REGEN_ENABLED` in case a keypress is orphaned (reload / alt-tab between the edges) and strands it at 0. Tooltips treat `macroDown` like `macro` (multi-line ⇒ macro-text tooltip via `ExsarLogic.IsSimpleCastMacro`).
- **Layouts.** `"horizontal"` / `"vertical"` (single row/column) or `"grid"` (fixed `col`/`row` per slot, width = widest column + 1). Grid supports the `hideWhenEmpty` / `groupFallback` **dynamic-row reflow**: out-of-stock `hideWhenEmpty` slots are hidden and remaining slots in the column collapse upward; a `groupFallback` slot shows as an empty placeholder when no member of its `col,row` group has stock (the Healthstone slot). Layout is protected — `ApplyLayout` runs only out of combat and re-runs on `PLAYER_REGEN_ENABLED`.
- **Item swapping.** `ranks` (highest-first interchangeable IDs → `SelectBestRank`) and `alternates` (first in-stock, zone-gated alts first → `SelectFirstInStock`) re-resolve the active item out of combat (`ResolveActiveAll`, combat-gated); the secure `item` attribute, icon, and count follow. `hideWhenEmpty` slots use the `item:<id>` attribute form (ranks share a name); others use the item name.
- **Cooldown sweep.** Item kind: the active item's own CD (read from bags via `C_Container.GetContainerItemCooldown` — TBC has no `GetItemCooldown`) or a player debuff (`cooldownDebuff`, e.g. Tinnitus for Drums, Recently Bandaged for bandages). Macro/spell kind: the longest-remaining of `cooldownItem` (resolved once via `GetItemInfoInstant`, classified by `CooldownState`), `cooldownSpell` (`GetSpellCooldown(spellName)` — e.g. a trap's cooldown), `cooldownTrinket` (`GetInventoryItemCooldown` for an equipped slot 13/14, without taking over icon/macro — for a spell+trinket burst macro), `cooldownDebuff`, and the **GCD**. Only a real item cooldown shows a countdown number; the brief GCD is sweep-only.
- **GCD swirl (automatic, default-UI behavior).** When no real CD is running, an on-GCD slot shows the live global-cooldown sweep — the same swirl the default action bars put on every on-GCD ability the instant you cast something. It's driven by `AB_GcdSpell(s)` (the slot's cast spell: auto-resolved `activeSpell` → `spell` → `cooldownSpell` → `iconSpell`, or an explicit `gcdSpell` override / `gcdSpell = false` to suppress): reading `GetSpellCooldown` on it **self-selects**, because on-GCD spells report the active GCD as their cooldown (classified `"gcd"` by `CooldownState`, i.e. 0 < duration ≤ 1.6s) while off-GCD spells (Auto Shot, Rapid Fire, Bestial Wrath, trinkets) report 0. So no per-bar flag is needed — every spell/trap/aspect slot across all bars gets the swirl automatically, and off-GCD slots never do. **Spell-less macro slots** (the all-in-one pet button, Steam Tonk — `resolveIcon`/`iconItem`, no resolvable cast spell) opt in with `gcd = true`, which forces the swirl via the shared `GetSpellCooldown("Wing Clip")` probe (Wing Clip has no CD of its own — same trick as `GlobalCooldownTracker`). The GCD swirl is sweep-only (no countdown number) and never dims the icon (`dimOnCooldown` is real-CD-only). The off-GCD Auto Shot macro sets `gcdSpell = false` so a heavily-hasted auto-shot reload timer can't masquerade as a GCD swirl.
- **Out-of-range red shade (`rangeCheck`).** The bar-level `rangeCheck = true` flag creates a translucent red wash (OVERLAY sub-level −1, above the icon and below the hotkey/count text) over each slot whose ability is **out of range of its target** — mirroring the default UI's red hotkey, but shading the whole icon. The target is **per-slot**: `rangeUnit` (default `"target"`) names the unit token whose range is checked — `"target"` covers both harm spells *and* friendly-target spells (Misdirection shades against a friendly target), `"pet"` covers pet-targeted abilities (Mend/Feed Pet). Each poll it resolves the slot's range spell via `AB_RangeSpell(s)` (spell/`spells` slots auto-use their cast spell `s.activeSpell`/`a.spell`; macro/item slots opt in with an explicit `rangeSpell = "<spell>"` string, or `rangeSpell = false` to suppress), checks the range unit is valid (`UnitExists` + not `UnitIsDead`), runs `IsSpellInRange(spell, rangeUnit)`, and gates the shade with `ExsarLogic.ShouldShowRangeShade(inRange, hasValidUnit)` (pure/tested: shade only when the unit is valid AND the result is exactly `0`; a `nil` result — wrong unit type for the spell, no range restriction, unknown spell, or unit not targetable — never shades). **No attackable-only gate:** `IsSpellInRange` returns `nil` whenever the spell can't act on the given unit (harm spell on a friendly target, or vice versa), so the shade self-selects per spell — that's what lets one engine path cover harm/friendly/pet abilities and auto-exclude aspects/traps/self-buffs (which read `nil`). Enabled on every bar that carries a target-checkable ability — `CoreCombatWidget` (the two pure-macro slots set `rangeSpell` to "Auto Shot" / "Raptor Strike"), `CooldownsWidget` (Intimidation), `UtilitiesWidget` (Tranquilizing Shot harm + Misdirection friendly), and `PetManagementWidget` (Mend Pet on the all-in-one slot + Feed Pet, both `rangeUnit = "pet"`). Bars whose every ability reads `nil` (Aspects self-buffs, Traps ground-placed) leave it off so the flag doesn't add idle `IsSpellInRange` calls for no effect.
- **Out-of-mana blue shade (`manaCheck`).** The bar-level `manaCheck = true` flag creates a translucent **blue** wash (same OVERLAY sub-level −1 placement as the range shade) over each slot whose spell is unusable **specifically for lack of mana/power** — mirroring the default UI's blue icon tint. Each poll it resolves the slot's mana spell via `AB_ManaSpell(s)` (same shape as `AB_RangeSpell` but a separate `manaSpell` field, since a slot's range spell and mana-cost spell can differ — the Auto Shot macro range-checks Auto Shot, which is free), reads `IsUsableSpell(spell)`'s **second** return (`notEnoughPower`), and gates the shade with `ExsarLogic.ShouldShowManaShade(noMana)` (pure/tested: shade iff `noMana` is truthy). Other unusable reasons (on cooldown, no target, not learned) leave the second return false, so they don't blue-shade. **Mana takes precedence over range:** the mana shade is computed first and, when shown, suppresses the range shade for that slot (one wash at a time; blue is the more actionable "you literally can't cast this" cue). Enabled on `CoreCombatWidget`, `CooldownsWidget`, `UtilitiesWidget`, `TrapsWidget` (each trap sets `manaSpell` since macro slots have no auto-resolved cast spell), and `PetManagementWidget` (the all-in-one's `manaSpell = "Mend Pet"`; `IsUsableSpell` reports no-mana only with a live pet, so the Revive/Call states stay clear). Aspects are left off (cheap toggles — would persistently blue-wash the whole bar while OOM for little value).
- **Trinkets & talent-gated spells (cooldowns-bar building blocks).** `trinketSlot` (13 top / 14 bottom) makes a macro slot that `/use`s the equipped trinket, with icon from `GetInventoryItemTexture` and CD from `GetInventoryItemCooldown` — follows gear swaps. `spells` (array of names or `{ name, id }`, preference order) makes a macro slot that `/cast`s each (first known fires — unknown `/cast` lines no-op, so spec substitutes are automatic); the icon + cooldown follow the first **known** spell (`AB_FirstKnownSpell`, via `IsSpellKnown(id)` with a name-lookup fallback), and the slot **hides** (`s.hidden`, packed out by horizontal/vertical `ApplyLayout`) when none are known — talent-irrelevant. `dimOnCooldown` (bar-level) dims macro/spell slots while a real CD runs (the brief GCD doesn't dim), like the item-kind on-CD dim.
- **Icons.** Static path (`icon`), item-derived (`iconItem` via `GetItemInfo`, `GET_ITEM_INFO_RECEIVED` retry), spell-derived (`iconSpell` via `GetSpellTexture`, `SPELLS_CHANGED` retry), **pet-state-dynamic** (`dynamicIcon`: map of `PetStateKey` → icon spec, re-resolved each poll, or a `resolveIcon(s, petState)` hook for state the engine can't see — e.g. the all-in-one Mend/Revive/Call button picks its icon from `UnitExists` + the widget's `IsPetDead()` verdict), equipped-trinket (`trinketSlot`), or first-known-spell (`spells`). `#showtooltip` auto-icon magic only applies to Blizzard action-bar buttons, not our secure buttons, hence the manual resolve.
- **Tooltips.** Item slots show the item tooltip (`SetItemByID`); `trinketSlot` shows the equipped item (`SetInventoryItem`). Macro/spell slots show the **associated spell's** tooltip (`GetSpellLink` → `SetHyperlink`), resolved as resolved `spells` entry → `spell` → `iconSpell` — **unless** the slot has a hand-written `macro` that is not a single `/cast` (`ExsarLogic.IsSimpleCastMacro`, pure/tested: ignores blank lines + `#directives`), in which case it shows its **macro text**. So Aspects/Traps (`/cast X`) show spell tooltips, while multi-action macros (Auto Shot start-attack, Raptor Strike weave, the Cooldowns spell+trinket combos) show their macro. `tooltipSpell` overrides: a spell name forces that spell, `false` forces macro text. A `tooltip(s, GameTooltip)` hook overrides everything.
- **Keybindings.** Named bindings `<bindingPrefix><i>` declared in `Bindings.xml`, bridged to `<buttonPrefix><i>` by `ExsarUI.SetupKeybindBridge`. **A `category="..."` attribute is required on the modern Anniversary client:** the Key Bindings panel groups by category, so a `header`-only binding registers (functionally bindable) but renders no section. Unlike `header` (resolved via a `BINDING_HEADER_*` global), `category` is displayed **literally**. The engine sets the `BINDING_NAME_*` (from `action.bindingLabel` or `action.name`) and optional `BINDING_HEADER_*` globals; labels are deliberately generic for slots that swap items so they stay accurate. Keys are assigned in **Blizzard's Key Bindings UI** (native conflict warning + account-sync; **no `ExsarAddonDB` entry**). Bindings are **positional**. On-icon hotkey label: top-right FontString (bottom-right is the count), text from `ExsarLogic.AbbreviateBindingKey(key)`.
- **`SetupKeybindBridge{ owner, bindingPrefix, buttonPrefix, count, onSlotKey, deps }`** mechanics: on its watcher-frame events (`UPDATE_BINDINGS` / `PLAYER_ENTERING_WORLD` / `PLAYER_REGEN_ENABLED`) it reads `GetBindingKey` and installs `SetOverrideBindingClick(owner, true, key, btn)` (override layer masks normal bindings, works in combat). The override calls are protected — skipped under `InCombatLockdown()`, re-applied on `PLAYER_REGEN_ENABLED`; `onSlotKey` always runs so labels stay current. `deps` injects WoW funcs for stub testing.

**`UsableItemsWidget.lua`** = `TRACKED_ITEMS` (item-kind, grid layout, `border = true`) + a `CreateActionBar` call. Tracks consumables in bags (mana/health potions with zone-gated `alternates`, Dark Rune, Drums of Battle via `cooldownDebuff = "Tinnitus"` + `useCharges`, Haste Potion, bandages via Recently Bandaged, Master Healthstone via `ranks` + `hideWhenEmpty`/`groupFallback`). 7 slots, `EXSAR_USE_ITEM1..7`, "ExsarAddon" category.

**`EngineeringWidget.lua`** = `TRACKED_ITEMS` (mixed item + macro kinds, horizontal layout, `border = true`) + a `CreateActionBar` call. Four item-kind gadgets from bags: Goblin Sapper Charge (10646), Super Sapper Charge (23827), Advanced Target Dummy (4392), Field Repair Bot 110G (34113) — no `ranks`/`alternates`, each a single item that greys out when out of stock, sweeps on its own item cooldown, and shows its **net charge count** (`countCharges = true`, summed across stacks). Plus one **macro-kind combo slot** ("Sappers"): a plain `macro` of two stacked `/use` lines — `/use Super Sapper Charge` then `/use Goblin Sapper Charge`, so the first usable line fires (Super Sapper's 1 min CD leads the Goblin Sapper's 5 min so both land in one fight). Static `iconItem = 23827` (Super Sapper icon), no cooldown field and no count (two different items would make a single count/sweep misleading). Plus one **macro-kind "Rocket Boots" slot** — a two-click equip/boost/swap-back workflow directly modelled on PetManagementWidget's Devilsaur Tooth prep slot, but for Goblin Rocket Boots (7189) in the feet slot (`INVSLOT_FEET` = 8): **click 1** (boots in bags) captures their `(bag, slot)` and `/equipslot`s them into the feet slot (the displaced boots bounce to those coords); **click 2** (boots equipped, **ready**) `/use`s the feet slot to fire the speed boost **alone**; **click 3** (boots equipped, **on cooldown**) `/use`s (a no-op while the on-use CD runs) AND `/equipslot`s the previous boots back. The swap-back `/equipslot` is appended **only when the boots' cooldown is active** (`BootsOnCooldown` via `GetInventoryItemCooldown` on slot 8 — the 30s just-equipped delay or the 5min on-use CD): unequipping the boots while the boost is live cancels it early, so a fresh `/use` must fire the boost by itself and the swap-back rides a later press once a cooldown is up. Dynamic via `resolveMacro`/`resolveBorderColor`/`getCooldown`/`isEnabled` closures (no static macro): `getCooldown` follows the boots (feet-slot CD when equipped, bag-item CD when carried), `isEnabled` greys when the boots are neither equipped nor in bags, and `resolveBorderColor` shows a single amber "SWAP BACK!" ring whenever the rockets are worn (no buff/spell-ID detection — the user chose one warning color; `/equipslot` is combat-blocked so a mid-combat boost leaves them on until you can swap, and the amber ring is the reminder). Swap coords persist in `ExsarAddonDB.engineering.rocketBootsSwap` (survives `/reload`). 6 slots, one keybind row each (`bindingCount` defaults to `#TRACKED_ITEMS`); adding a gadget means appending to `TRACKED_ITEMS` **and** a matching `EXSAR_ENGINEERING<n>` line in `Bindings.xml` (keep the two in lockstep). `EXSAR_ENGINEERING1..6`, "ExsarAddon Engineering" category.

**`PetManagementWidget.lua`** = `PET_ACTIONS` (macro-kind, horizontal layout, `rangeCheck = true`, `manaCheck = true`) + a `CreateActionBar` call. The all-in-one (Mend Pet) and Feed Pet slots set `rangeSpell` + `rangeUnit = "pet"` so they red-shade when out of pet range; the all-in-one only shades in its Mend (live-pet) state since an absent/dead pet fails the `rangeUnit` exists+alive gate. The all-in-one also sets `manaSpell = "Mend Pet"` to blue-shade when you can't afford Mend Pet (blue takes precedence over red); `IsUsableSpell` reports no-mana only with a live pet, so the Revive/Call states stay clear. Other slots (no `rangeSpell`/`manaSpell`) never shade. Pet actions: all-in-one Mend/Revive/Call (`resolveIcon` + `resolveMacro`, never greyed; chosen by pet state, not one static conditional macro. **The hard problem: a dead pet whose corpse has despawned is INDISTINGUISHABLE from a dismissed pet** — once the body is gone the "pet" token vanishes and `UnitExists`/`UnitIsDead`/`UnitHealth`/`GetPetHappiness`/`HasPetUI` all read false/false/0/nil/false for both (verified in-game; with the corpse still up the token exists and `[@pet,dead]` works normally). So the dead-vs-dismissed verdict can't be queried — it's tracked statefully in this file (`IsPetDead()`, persisted to `petManagement.petDead`): combat-log `UNIT_DIED`/`UNIT_DESTROYED` for the pet's GUID sets it (survives the corpse despawning), `UNIT_PET` with a live/absent token clears/confirms it, a dismiss leaves it false. Three states: **have a pet** (`UnitExists` — alive or corpse-present dead) → `/cast [@pet,exists,nodead] Mend Pet` + `/stopmacro [@pet,exists,nodead]` + ungated `/cast Revive Pet` (the ungated fallback revives a pet that dies mid-combat, since secure macros can't be rewritten in combat; the Mend gate needs `exists` because `[@pet,nodead]` alone is TRUE for an absent unit); **dead, corpse gone** (`IsPetDead`) → `/cast Revive Pet`; **dismissed/petless** → `/cast Call Pet`. Revive and Call can't share one static macro — an ungated `/cast` of either locks the keypress when it can't fire (client commits to the first reachable `/cast`), starving the other — hence the `IsPetDead()` split. Survives combat without a rewrite — you pull with a live pet so the "have a pet" variant is loaded, and when it dies that frozen variant already revives via the ungated line, no combat-blocked `SecureSetAttribute` needed), Send to Attack, Recall, Dismiss, Steam Tonk save trick (`cooldownItem` + `countCharges`, `requires="notdead"`), Feed Pet (`countItem = "Clefthoof Ribs"`), and Devilsaur Tooth Prep (see below). All macros are **fully addon-controlled** — no user override, no config-panel macro editing, no persisted macro DB. 7 slots, `EXSAR_PET_ACTION1..7`, "ExsarAddon Pet" category. `MAX_SLOTS` must stay equal to the `EXSAR_PET_ACTION` binding count in `Bindings.xml` — grow `PET_ACTIONS`, `MAX_SLOTS`, and `Bindings.xml` together.

**Devilsaur Tooth Prep slot** — a boss-fight preflight workflow. The Devilsaur Tooth (item 19992) puts a +crit buff (spell 24353) on the pet, but is a bad combat trinket otherwise, so the goal is to apply the buff pre-pull and re-equip the previous trinket before combat starts. Two-click state machine, all dynamic via the engine's `resolveMacro` / `resolveBorderColor` / `getCooldown` / `isEnabled` hooks (no static `macro`):
- **Click 1** (`stage == "bagged"` per `ExsarLogic.DevilsaurStage`): scan bags for the Tooth, remember its `(bag, slot)` coords in `ExsarAddonDB.petManagement.devilsaurSwap` (persisted so the workflow survives `/reload`), then `/equipslot 13 <bag> <slot>` to swap it into the top trinket slot. The previously-equipped trinket bounces into those same coords — that's why we anchor by bag slot, not item identity.
- **Click 2** (`stage == "equipped_unused"`, yellow border = "USE!"): after the 30s "just equipped" cooldown sweep drains, `/use 13` (applies the buff to the pet) + `/equipslot 13 <stored bag> <stored slot>` (swaps the previous trinket back) — both lines in one macro. Normally this leaves no border and the buff ticks on the pet.
- **Red border = "UNEQUIP!"** (`stage == "equipped_buffed"`): the `/use` succeeded but the `/equipslot` half didn't (combat started, bag slot was disturbed). The slot persists in this state until the user manually swaps; clicking re-fires the same use+swap macro (the `/use` no-ops because it's on CD).
- **Cooldown source switches by stage** — slot 13's CD when the Tooth is equipped (catches the 30s equip CD and the post-use CD), bag-item CD when it's carried (so the previous trinket's CD never bleeds through). **Greyed** when there's no live pet OR no Tooth anywhere.

**Shared hunter-swing trackers (`ExsarUI.CreateAutoShotTracker` / `CreateMeleeSwingTracker`) structure:**
- Both are event-driven state objects created once and shared via lazy singletons (`ExsarUI.GetAutoShotTracker` / `GetMeleeSwingTracker`). They exist so `AutoShotMonitor` and `MeleeWeaveHelper` read **one** source of truth instead of each re-deriving the auto/melee cycle. **They deliberately mirror — not refactor — the proven event logic already in `RangedSwingTimer` (ranged) and `MeleeRangeIndicator` (melee):** those two modules predate the trackers and keep their own copies. This is an accepted, documented duplication (avoids destabilizing tuned code); the two older modules could adopt the shared trackers in a later consolidation. **When touching the auto/melee cycle logic, keep the tracker and its origin module in sync** (Aimed Shot IDs, Feign Death handling, speed refresh) — same discipline as the `AIMED_SHOT_IDS` tables across RangedSwingTimer/CastBar/MeleeRangeIndicator.
- Auto tracker fields: `lastShotTime`, `speed`, `baseSpeed`, `castEnd`, `autoFired`, `autoRepeatOn` (toggled by `START/STOP_AUTOREPEAT_SPELL`). Methods `:TimeToNextAuto(now)` (nil if no cycle) and `:Overdue(now, predictGrace, overdueGrace)` (→ `ExsarLogic.AutoShotDelay`, gated on `autoFired`). **Fired callback:** `T:OnAutoShot(fn)` registers a fn called with `(firedTime, delay)` when an auto lands — `delay` = `ExsarLogic.AutoShotFiredDelay` against the cycle that just ended, computed *before* `lastShotTime` is overwritten (nil when there was no cycle, e.g. the first shot after Feign Death). Both timestamps are event-receipt times, so the shared event latency cancels out of the difference — unlike the live `:Overdue` counter, which reads ~0.1s late every cycle and needs `CLIP_OVERDUE_GRACE` to compensate. FD clears the cycle; the FD buff fading (`UNIT_AURA` + `PlayerHasBuff`) restarts it; Aimed Shot landing resets `lastShotTime`; `autoFired` clears on `PLAYER_REGEN_ENABLED`.
- Melee tracker fields: `speed`, `lastSwing`, `swingActive`, `lastPress`. Method `:Ready(now, lookahead)` — never-swung reads ready (a step-in swings immediately); else `now - lastSwing >= speed - lookahead`. Combat-log `SWING_DAMAGE/MISSED` + Raptor Strike IDs advance the swing; FD/Aimed resets mirror `MeleeRangeIndicator`. **Landed callback:** `M:OnLanded(fn)` registers a fn fired with the landing time when a melee attack *connects* (`SWING_DAMAGE` or a Raptor `SPELL_DAMAGE` — not a miss); swing TIMING still advances on both hits and misses. One combat-log parse serves both signals (avoids a second `COMBAT_LOG_EVENT_UNFILTERED` listener — matters in raids). **Press stamp:** `M:NotePress(now)` records the weave-macro press (called from `CoreCombatWidget`'s Raptor slot `postClick`); `lastPress` + the landing time are what let `MeleeWeaveHelper` identify a stale-position melee retry.

**`AutoShotMonitor.lua` structure:**
- Two independent signals, both off the shared auto-shot tracker; the frame (`bgAlpha = 0`) only draws elements when there is something to say (silent otherwise). Poll 0.05s.
- **OVERDUE readout:** `tracker:Overdue(now, ...)` → a big value + small caption. `predicted` (a cast will end past the due time) → red **CLIP** + `%.2f`; else → orange **Auto overdue** + `+%.1f` live counter. Same value `RangedSwingTimer` shows inline (`CLIP_PREDICT_GRACE` 0.02 / `CLIP_OVERDUE_GRACE` 0.2).
- **REACTIVATE AUTO! alarm:** `ExsarLogic.ShouldReactivateAuto(IsSpellInRange(autoShotName,"target"), tracker.autoRepeatOn, hasTarget)` — fires when Auto Shot reports in range (1 ⇒ past the 5yd dead zone AND within shooting range) but auto-repeat is OFF. Keyed on auto-repeat-off (NOT overdue) so it stays silent while kiting with auto on. Pulses via `ExsarLogic.PulseAlpha` on the frame's OnUpdate (only the alarm text pulses; the overdue number stays steady/readable).
- **Per-shot CLIP feedback (comic pop).** The overdue readout vanishes the instant the shot fires — exactly when the player is looking — so each landed auto restates the verdict as a `ExsarUI.CreateComicPop` pop lasting `POP_DUR` (0.8s), same effect as `MeleeWeaveHelper`'s hit/miss text: green **NO CLIP!** on a clean cycle, else the amount (**CLIP +0.34**) in orange, red past `CLIP_SEVERE` (0.5s). Driven by `tracker:OnAutoShot` → `ExsarLogic.ClipVerdict(delay, CLIP_CLEAN_GRACE = 0.1, CLIP_SEVERE)`. The retrospective `delay` carries no latency bias (see the tracker note), so the 0.1s clean grace is honest — do NOT reuse `CLIP_OVERDUE_GRACE` here. Gated on context + in-combat, and on `ExsarAddonDB.autoShotMonitor.clipFeedback` (default ON; "Clip feedback text" checkbox). A `nil` delay (no cycle to score) never pops.
- Visibility: hidden unless context-enabled (`enableSolo/enableParty/enableRaid` via `ExsarLogic.AggroAlertEnabled`); active when in combat + attackable target; when unlocked and inactive it shows a **dimmed static preview** of its real content (example "Auto overdue +1.3" + "REACTIVATE AUTO!") so the true footprint is visible for positioning. A `mode`-gated `EnterMode` runs the clear only on transitions so a static preview doesn't hide-then-show (flicker). Slash `/exsar autoshotreset`.

**`MeleeWeaveHelper.lua` structure:**
- A single binary **WEAVE NOW!** cue + a countdown bar (drains right→left) and numeric seconds of the window remaining. Poll 0.05s. It is a **forgiving training cue, not a metronome** — the honest correction is `AutoShotMonitor`'s overdue readout, so its defaults are realistic (grounded in the mechanics, not padded) and it leans on hysteresis smoothing rather than loose thresholds for its forgiveness.
- **Decision (`ExsarLogic.WeaveNowState`, pure/tested):** `WEAVE NOW = meleeReady AND not casting AND weaveCost < timeToAuto AND (timeToAuto − gcdRemaining) < steadyCastTime`. The last term is the crux — weave only when a shot won't fit before the auto *after* the GCD lockout. Subtracting `gcdRemaining` (not a boolean on-GCD) is the precise form of the old "on-GCD OR no-room" rule: it still lights the cue in the arcane/multi GCD gap (locked out, leftover won't fit a Steady), the slow post-cast tail, and the fast auto-auto gap — but NOT in the fresh-cycle GCD tail right after an auto (a full Steady still fits → cast it, don't weave). That fixed a spurious one-frame flash at the start of the auto cooldown. `windowRemaining = timeToAuto − weaveCost` drives the countdown; it self-scales with haste for free. `steadyCastTime` = `ExsarLogic.HastedCastTime(1.5, speed, baseSpeed)` + `shotFitBuffer`.
- **Inputs:** melee-ready from the shared melee tracker; `timeToAuto`/`speed`/`baseSpeed` from the shared auto tracker; `gcdRemaining` from `GetSpellCooldown("Wing Clip")` (no CD of its own → reports the GCD); `casting` from `UnitCastingInfo("player")` (moving cancels a cast → never cue mid-cast).
- **Cast-start race guard (`GCD_SETTLE` 0.15s):** `GetSpellCooldown` can report the new GCD a frame *before* `UNIT_SPELLCAST_START`/`UnitCastingInfo` see the cast, so for one poll the logic reads "GCD active, not casting" at the start of a Steady and (amplified by the hysteresis hold) flashes the cue. Fix: track `gcdRemaining` every poll (even out of weave range) and when it **jumps up** (a new GCD started) arm `gcdSettleUntil = now + GCD_SETTLE`; while within that window `casting` is forced true so the cue can't fire. Safe because a freshly-started GCD is either a cast beginning (must not cue) or an instant shot (a ~0.15s delay on that legit gap is imperceptible).
- **Anti-flicker:** `ExsarLogic.HoldCue(rawOn, now, holdUntil, cueMinOnTime)` holds the cue on for `cueMinOnTime` after the raw condition drops, so input jitter reads as "window open" held, not a strobe. `windowMax` is captured as the cue opens so the bar drains from full.
- **Smooth countdown:** the 0.05s poll only makes the show/hide decision; the countdown bar is redrawn every frame in `frame:OnUpdate` (recomputing `windowRemaining` live from the auto cycle) so it drains smoothly instead of stepping at 20fps. `S.weaveCost` is cached each poll so the per-frame render is cheap.
- **Unlocked preview:** when unlocked and not actively cueing, it shows a **dimmed static preview** (`ShowPreviewContent` → `ShowCue(0.6)` with `windowMax=1`) — the real "WEAVE NOW!" text + a partly-full bar — so the footprint is visible for positioning (replaces the old grey placeholder).
- **Range/context gating:** only active in weave range (≤8yd — `maxR` from `ExsarUI.ProbeRangeBracket("target", WEAVE_CHECKERS)`, where `WEAVE_CHECKERS` = Wing Clip 5yd + Attuned Crystal Cores 8yd) AND context-enabled (solo/party/raid). Self-silences on pure-ranged fights with no toggling.
- **Hit/late/miss feedback (comic-pop text).** Three states, all via the shared melee tracker's `OnLanded(landedTime)` callback and the poll's window lifecycle:
  - **WEAVE HIT!** (green) — a melee attack landed within `RETRY_THRESHOLD` (0.35s) of the weave-macro press: a clean weave.
  - **LATE - TAP STRAFE** (orange, smaller face `POP_FONT_LATE`) — the swing landed but only after the **500ms stale-position melee retry** (see "The Melee Retry Timer" in the Hunter timing reference). Classified by `ExsarLogic.MeleeRetryDelay(melee.lastPress, landedTime, RETRY_THRESHOLD, PRESS_ATTRIB_WIN)` (pure/tested): press→landed latency is bimodal (~0.11s clean vs ~0.61s retried) so one threshold separates them, and a swing outside the 3s attribution window belongs to no press (an auto-attack continuation) and never pops LATE. The press timestamp comes from `CoreCombatWidget`'s Raptor slot `postClick` → `melee:NotePress(GetTime())`. **This is the coaching signal** — the delay is avoidable by tapping a movement key before the macro.
  - **WEAVE MISS!** (red) — the window expired unweaved. **Keyed on the auto shot actually firing, not on a predicted deadline.** The raw window closes ~`weaveCost` (0.4s) *before* the auto, and a retried swing can still land in that gap, so popping at window-close produced a spurious MISS immediately followed by a HIT. Instead, an expired window with no landed swing **arms** a pending MISS (`missPending`, `missAnchor = auto.lastShotTime`), which resolves when `auto.lastShotTime` advances (the auto fired ⇒ real MISS) or is cancelled by any landed swing. `MISS_MAX_WAIT` (1.5s) drops a pending MISS if no auto ever comes (auto-repeat off, target died) rather than stranding it into the next pull.

  The lifecycle is keyed on the RAW window (not the hysteresis display): `windowOpen`/`hitDuringWindow` tracked in the poll; MISS is armed only when the window closed by *expiry* (`timeToAuto` fell to `weaveCost`), NOT when it closed because you cast or stepped out of range. The pop comes from the shared `ExsarUI.CreateComicPop` (UIParent-child frame anchored to the widget, so it shows even when the widget frame is hidden; overshoot scale pop → float up `POP_RISE` → fade over `POP_DUR` 0.8s; scales with the widget's config scale). Toggle: `ExsarAddonDB.meleeWeave.feedback` (default ON; "Hit / miss feedback text" checkbox) — note `OnMeleeLanded` still maintains `hitDuringWindow`/`missPending` when feedback is off (only `TriggerPop` is gated), so re-enabling mid-fight can't strand a pending MISS.
- **Windfury proc flourish (`windfuryEffect`, default ON).** A pure eye-candy reward: on a Windfury extra-attack landing on the player's melee (Windfury Totem from a group shaman), an arcing crescent blade-slash (`ExsarUI.CreateSlashEffect`, `SLASH_DURATION` 0.8s) + a "whoosh" via `PlayWindfurySound()`, which plays a **custom bundled sound** (`WINDFURY_SOUND` = `Sounds\windfury.ogg`) and **falls back** to the built-in Whirlwind whoosh (`WINDFURY_SOUND_FALLBACK` = 568519) when that file is absent (`PlaySoundFile` returns `willPlay=false`). Drop your own `.ogg` in `Sounds/` — a NEWLY added sound file needs a full client **restart** (not just `/reload`; WoW indexes sound files at launch), `.wav` is unsupported on the Anniversary client. See `Sounds/README.md`. Detected via the shared melee tracker's `OnWindfury` callback (off the same single combat-log parse — `ExsarLogic.IsWindfuryProc` matches the `SPELL_EXTRA_ATTACKS` subevent by name, so all ranks/sources count). Windfury Totem grants a **single** extra attack (one `SPELL_EXTRA_ATTACKS` proc — no de-dupe needed; only the shaman's own Windfury Weapon procs two attacks). Gated on the toggle + solo/party/raid context + in-combat. (The slash effect is anchored to the widget's own UIParent-child frame, so it fires even when the WEAVE NOW cue is hidden.) **While the widget is unlocked** the slash also **loops silently** (re-fired every `WF_PREVIEW_INTERVAL` = `SLASH_DURATION` + 0.6s, no whoosh, whenever `windfuryEffect` is enabled) so its placement can be previewed for positioning.
- **Knobs (all config sliders, realistic defaults grounded in the mechanics):** `weaveCost` (0.4 — in+swing+out), `shotFitBuffer` (0.1 — reaction/latency margin on "cast finishes before the auto is due"), `meleeReadyLookahead` (0.1 — step-in lead), `cueMinOnTime` (0.1 — minimal anti-flicker). Raising `weaveCost`/`shotFitBuffer` lights the cue in more of the cycle; lowering defers to shooting. Read live so slider edits apply immediately. Slash `/exsar weavereset`; `/exsar wftest` force-fires the flourish; `/exsar slashtex [path]` swaps the slash brush texture live (cycles a soft-glow candidate list when given no path) to A/B textures without a `/reload`. (`/exsar` sub-command handlers now receive the message remainder as their one arg — `slashHandlers[cmd](msg:match("^%S+%s+(.*)$"))` in `Core.lua`; existing no-arg handlers ignore it.)
- **In-game unknowns to verify/tune:** `START/STOP_AUTOREPEAT_SPELL` reliability (the auto-repeat boolean feeding both the tracker and the reactivate alarm — flagged as sometimes unreliable post-FD); and the knob defaults (tune at the target dummy).

## Key WoW API Used

- `GetSpellInfo(spellName)` — returns name, rank, icon texture path for the highest-learned rank
- `GetSpellCooldown(spellName)` — returns `start, duration, enable`; `start=0` means no cooldown
- `IsSpellKnown(spellId)` — checks if a spell is in the player's spellbook (modern client); falls back to `GetSpellInfo ~= nil`
- `CooldownFrameTemplate` — built-in frame template providing the circular sweep animation
- `SetDesaturated(bool)` — grays out a texture
- `SetCooldown(start, duration)` — drives the sweep on a Cooldown frame
- `CombatLogGetCurrentEventInfo()` — unpacks combat log event data; required on TBC Classic Anniversary (modern client); replaces the old variadic-args approach
- `texture:SetMask(path)` — clips a texture to the shape of a mask image; used for circular glow discs; wrapped in `pcall` for safety
- `UnitExists("pet")` — true when the player has an active pet
- `PlaySound(soundKitID [, channel])` — plays a built-in sound; use `"Master"` channel for alerts that must be heard regardless of SFX volume. Only accepts **SoundKit IDs** (small numbers, e.g. 154, 1024) — passing a FileDataID silently does nothing.
- `PlaySoundFile(fileDataID or path [, channel])` — plays a sound by **FileDataID** (the large 6-digit IDs, e.g. 567947) or file path; use this, not `PlaySound`, when the ID came from a sound-file database
- `IsInRaid()` / `IsInGroup()` — group context detection; solo = not `IsInGroup()`
- `UnitIsUnit(unit1, unit2)` — true if both unit tokens refer to the same entity
- `IsItemInRange(itemID, unit)` — returns `true`/`false` if the item's range to `unit` can be checked, else `nil`. Works with **any** item ID (the item need not be in your bags), but only if the item exists in the current client's DB — IDs from later expansions return `nil`. Querying an **enemy** unit in combat is permitted (Blizzard re-allowed this in Dec 2023 after a brief 2023 protection). Used by `RangeToTargetWidget` for fixed-range distance bracketing. Items with a min range as well as a max would corrupt a `≤range` bracket, so only no-minimum harm items are used.
- `IsSpellInRange(spellName, unit)` — returns `1`/`0`/`nil`. Works in combat. A spell with a **minimum** range (dead zone, e.g. Auto Shot) returns `0` when too close as well as too far, so such spells are NOT valid as simple `≤range` checkers — `RangeToTargetWidget` only uses Wing Clip (melee, no minimum) as a spell checker. WoW exposes no exact unit distance; bracketing multiple range checks (LibRangeCheck / RangeDisplay approach) is the only way to estimate it.
- `Bindings.xml` + `GetBindingKey(command)` / `SetOverrideBindingClick(owner, isPriority, key, buttonName)` / `ClearOverrideBindings(owner)` — keybinding bridge. A named binding declared in `Bindings.xml` appears in Blizzard's Key Bindings UI (native conflict warning, account-synced). `GetBindingKey("EXSAR_USE_ITEM1")` returns the assigned key(s); `SetOverrideBindingClick` then maps that key to a secure button click in a **higher-priority override layer** that masks (does not unbind) the normal binding while active — this is what lets the bound key use an item in combat. `SetOverrideBindingClick` / `ClearOverrideBindings` are **protected**: they cannot run during `InCombatLockdown()`, so defer and re-apply on `PLAYER_REGEN_ENABLED`. Used by `UsableItemsWidget` via `ExsarUI.SetupKeybindBridge`.
- `GetWeaponEnchantInfo()` — returns `hasMainEnchant, mainExpMs, mainCharges, mainEnchantId, hasOffEnchant, ...`; `mainExpMs` is milliseconds remaining; returns only remaining time, NOT total duration — total duration must be hardcoded if needed (e.g. for sweep animation). Returns the off-hand equivalents (`hasOffEnchant, offExpMs, offCharges, offEnchantId`) as returns 5–8. Use the enchant IDs to distinguish between different temporary enchants (e.g. Adamantite Sharpening Stone = 2713, Adamantite Weightstone = 2955, Windfury Weapon = 2636)

|---|---|---|---|
| Auto Shot wind-up | 0.5s | Yes | `0.5 / totalRangedHaste` |
| Auto Shot cooldown | `weaponSpeed - 0.5` | Yes | `(weaponSpeed - 0.5) / totalRangedHaste` |
| Full Auto Shot cycle | `weaponSpeed` | Yes | `weaponSpeed / totalRangedHaste` (= effective weapon speed) |
| Steady Shot | 1.5s | Yes | `1.5 / totalRangedHaste` |
| Multi-Shot | 0.5s | Yes | `0.5 / totalRangedHaste` (NOT instant — same base as Auto Shot wind-up) |
| Arcane Shot | ~0.1s | No | Fixed; effectively instant |
| GCD | 1.5s | **No** | Fixed at 1.5s; ranged GCD is NOT reduced by haste in TBC |
| Melee weave | ~0.4s | No | Fixed time to step in, swing, step out |

### Haste Stacking

Haste sources stack **multiplicatively** (buff-based) on top of an **additive** haste-rating base:

```
base_haste = 1 + haste_rating / 1577   (15.8 rating = 1% haste at level 70)
-- Drums of Battle (+80 rating = +5.06%) and Haste Potion (+400 rating = +25.32%)
-- are additive with haste rating, applied before multiplicative buffs.

general_haste = base_haste * [bloodlust 1.30 if active]
ranged_haste  = general_haste * 1.15(quiver) * 1.20(Serpent's Swiftness 5/5)
                * [1.40 Rapid Fire if active] * [1.15 Imp Hawk proc if active]
```

### Key Haste Source Values

| Source | Multiplier | Scope |
|---|---|---|
| Quiver (15%) | ×1.15 | Ranged only |
| Serpent's Swiftness (BM 5/5) | ×1.20 | Ranged only |
| Rapid Fire | ×1.40 | Ranged only; 15s duration (19s with 2pc T3) |
| Imp Aspect of the Hawk (5/5) | ×1.15 | Ranged only; 10% proc chance, 12s duration |
| Bloodlust / Heroism | ×1.30 | Both melee and ranged |
| Drums of Battle | +5.06% | Additive with haste rating |
| Haste Potion | +25.32% | Additive with haste rating |

### Auto Shot Cycle Model

The auto shot cycle has two phases:
1. **Wind-up (cast)**: 0.5s base, haste-reduced — hunter must be stationary
2. **Cooldown**: `(weaponSpeed - 0.5) / haste` — free to move or cast other spells

When standing still, the game auto-starts the wind-up so it completes exactly at cycle end. When stopping from movement, the full unhasted 0.5s wind-up plays from the stop point (observed in-game; the sim does not model movement).

**Clipping**: If a cast (Steady Shot, etc.) is still in progress when the auto shot becomes available, the auto is delayed until the cast finishes. The delay = `castEndTime - autoAvailableTime`.

### The Retry Timer (hidden 500ms auto-shot resume delay)

Source: Blizzard "Not A Bug" blue post — [Classic Hunter: The Retry Timer](https://us.forums.blizzard.com/en/wow/t/classic-hunter-the-retry-timer/542470). This is **intentional reference-client behavior**, not spell batching and not a server heartbeat, and it is the mechanic behind "the cast bar finished / the swing timer emptied but the shot doesn't fire for another fraction of a second."

**Mechanic.** Auto Shot does not fire the instant it becomes eligible. The client runs a hidden **retry timer** that periodically re-attempts to (re)start Auto Shot, and that timer **refreshes on a 500ms cadence**. Whenever Auto Shot cannot fire the moment the swing cooldown ends — because you were moving, because a cast/GCD was occupying the shot, or because auto-repeat was toggled — the game waits for the **next retry tick** to try again. The gap between "eligible" and "next retry tick" is dead time of **0 to ~0.5s**, on top of the normal wind-up. It is not deterministic from the client's side: you can't see the retry timer's phase, only its effect.

**Triggers** (from the blue post):
1. **Movement** — the retry timer checks for movement before resuming; it refreshes every 500ms *while moving*. Stop moving just after a tick and you wait up to ~0.5s for the next check to observe you're stationary.
2. **Casting a shot with a cast time** — Aimed Shot, Multi-Shot, Steady Shot, Volley all start the retry timer *in the background during the cast*. **Any Auto Shot that follows one of these can be delayed by up to 0.5s before it even begins its wind-up** — and this happens **even while standing perfectly still**. This is the case that bites a standard Steady-Shot weave rotation.
3. **Feign Death** resume — compounded delay on the post-FD Auto Shot.
4. **Double-tapping the Auto Shot toggle/macro** while already shooting — starts a retry cycle, up to 0.5s.
5. **Toggling Auto Shot on while a melee ability (Raptor Strike) is up** — instant retry failure.
6. **Re-enabling Auto Shot before the swing completes** — delay up to a full 3.4s.

**Key consequence for widgets:** the visible cast/aim bar and the swing-timer bar predict when the shot is *due*; the retry timer means the shot can *actually* land 0–0.5s after that predicted moment. That trailing "due but not yet fired" window is exactly what the user must be told **not to act in** (starting Steady Shot there clips the pending auto). We surface it as the **overdue delay counter** in `RangedSwingTimer` (`ExsarLogic.AutoShotDelay` orange live counter — the "shot past due, hasn't fired" regime): that counter *is* the retry-timer window made visible. Because the retry delay is not observable in advance, the only honest signal is reactive — show the time elapsed since the shot became due until `UNIT_SPELLCAST_SUCCEEDED` lands. Note the `CLIP_OVERDUE_GRACE` (0.2s) suppression: event latency makes every normal cycle read ~0.1s late, so short retry gaps below the grace are currently hidden.

### The Melee Retry Timer (position snapshot; why white swings "don't go off")

The melee analogue of the auto-shot retry timer above, and the reason a melee weave often produces **no white swing at all** even though the swing timer was ready and you were visibly in melee range.

**Mechanic.** The server does not track your position continuously. It **snapshots** it on:
1. a **movement key down** (not key up),
2. a **spell cast**, or
3. **0.5s after** either of the above.

`/startattack` evaluates melee range against that snapshot. Step in from range and press the macro immediately and the server may still hold your *pre-step* position, fail the range check, and put the attack on a **0.5s melee retry timer**. The swing then lands ~0.5s late, or — if you have already stepped back out by the time the retry fires — never.

**Raptor Strike is immune.** It is a spell cast, so it refreshes the position snapshot before it executes. Verified in the combat logs: 71/71 Raptor Strikes had `SPELL_CAST_SUCCESS` and `SPELL_DAMAGE` in the **same millisecond**. (This does not by itself settle whether Raptor is instant or on-next-swing — queuing emits no combat-log event, and its 6s cooldown exceeds the ~3.6s swing cycle, so the swing was always ready when pressed.)

**Empirical signature** (two logged sessions, 2026-07-08, 2H, 3.59s swing cycle). Time from macro press to white `SWING_DAMAGE` is sharply **bimodal**:

| mode | latency | n | meaning |
|---|---|---|---|
| fast | 0.02–0.15s (tight around **0.11**) | 16 | snapshot was fresh; attack started immediately |
| slow | 0.46–0.62s (tight around **0.61**) | 12 | snapshot was stale; one 500ms retry tick |

The modes are **exactly 0.50s apart** with negligible within-mode spread — the fingerprint of a periodic gate, not of a residual swing timer. On every swing, "time since previous melee attack" was 3.5–5.9s, i.e. **at or above the swing cycle**: the swing was always available before the press. Server-side position at press time was 5.0–5.9 yd in *both* modes (swings land at 3.9–5.6 yd), so the weave is always executed right at the range boundary — which is why the failure is intermittent rather than constant.

**Mashing makes it worse.** Each failed `/startattack` latches the retry timer. Logged dead presses (a press producing no melee attack within 3s): **49/99** while mashing (2.68 presses per Raptor) vs **19/72** pressing more sparingly (2.12 per Raptor).

**Correct technique — and it differs per attack:**
- **Raptor Strike**: step in → press macro → step out.
- **White swing**: step in → *start stepping out* → press macro. The backward movement key-down snapshots you while still in range, so the attack passes its check. Any movement tap works (backpedal/strafe); it must be **key down**, within 0.5s of the press.

The `Grounded` weave addon mitigates this by firing `/stopattack` on **key up**, which un-latches the retry timer between presses so mashing is safe. **We now do this natively** — `CoreCombatWidget`'s Raptor Strike slot is a dual-edge (`macroDown`/`macroUp`) action-bar slot, so no Grounded dependency. (Grounded is also fragile: its `PLAYER_LOGIN` runs a cosmetic `hooksecurefunc("SpellBookFrame_Update", ...)` four lines *before* `UpdateSecureButtons()`, so on a client that no longer exports that global the hook throws and **none** of its binds are ever created — the reported "replace line 56" bug.)

**Consequence for widgets.** The 0.5s is **avoidable, not intrinsic** — so do NOT inflate `MeleeWeaveHelper`'s `weaveCost` to budget for it (0.4s remains the cost of a correctly-executed weave; a larger value would open the cue early on every weave and silently reward bad technique). Instead the delay should be **detected and coached**: the addon owns the weave macro button, so it can timestamp the click and measure click → `SWING_DAMAGE`. A swing landing ≳0.35s late is a positively-identified stale-position retry, and is worth surfacing as its own feedback state.

**Sources.** Hunter Discord, 2026-07-08 (Joosy, Elven), corroborated by combat-log analysis. Combat logs **cannot** confirm this by correlation: the position refreshes that matter are movement key-downs, which emit no combat-log event. A distance-at-press test over the *observable* (spell-cast) refreshes correctly comes back null — fast and slow weaves are indistinguishable there (median 5.34 yd vs 5.13 yd, refresh age 0.28s vs 0.27s).

**CONFIRMED BY INTERVENTION (2026-07-08).** Tapping strafe/backpedal immediately before the macro eliminates the retry mode:

| run | on-CD presses → white swing | white swings per Raptor | fast (non-retry) |
|---|---|---|---|
| baseline (mashing, no tap) | 13/62 (21%) | 0.32 | 18% (n=11) |
| transitional | 17/38 (45%) | 0.50 | 86% (n=14) |
| tap, 192s run | 12/16 (75%) | 0.63 | **100%** (n=12), max latency 0.12s |
| tap, 300s run | 19/23 (83%) | **0.83** | 89% (n=19) |

Dead presses (a press yielding no melee attack within 3s) fell 49% → ~9%; 0.83 white swings per Raptor approaches the ~1.0 ceiling implied by the 6s Raptor cooldown against the 3.59s swing cycle. **Caveat:** presses-per-Raptor also drifted down (2.68 → 1.84), so reduced mashing is entangled with the tap; but the ~0.61s retry mode is the tap-specific signature and it went from 82% of swings to 0–11%. The measured press→swing histogram is **empty between 0.2s and 0.5s** across every run, which is what makes `RETRY_THRESHOLD = 0.35` unable to misclassify a borderline swing.

### Widget Implications

- **Swing timer reticules**: Mark the hasted clip window (`0.5 / haste + latency`) — shows when starting a new cast would delay the next auto shot
- **Cast bar (standing still auto aim)**: Uses hasted clip window duration
- **Cast bar (after stopping from movement)**: Uses unhasted 0.5s + latency — the actual wind-up time
- **Cast bar (Multi-Shot)**: Should use `0.5 / haste`, NOT a fixed 0.5s
- **GCD tracker**: Must use fixed 1.5s, NOT haste-reduced

## SecureActionButtonTemplate in TBC Classic Anniversary

TBC Classic Anniversary uses the modern WoW client with `ActionButtonUseKeyDown = 1` by default. `SecureActionButton_OnClick` only fires on **down** events, so buttons registered with only `"AnyUp"` silently do nothing. Always use:
```lua
btn:RegisterForClicks("AnyUp", "AnyDown")
```
Avoid adding non-secure `SetScript("OnClick")` or `HookScript("OnClick")` to a `SecureActionButtonTemplate` button — this can taint the button and prevent the secure action. Use `PreClick`/`PostClick` for any surrounding logic instead. Also avoid cross-parent `SetAllPoints` anchoring on secure buttons (e.g. a UIParent-child secure button anchored to a child of a custom frame) — the anchor silently fails and `GetCenter()` returns nil.
